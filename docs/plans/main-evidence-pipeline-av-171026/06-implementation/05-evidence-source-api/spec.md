# Evidence & Source API — agent_run_files, evidence views, whatsapp source

## Overview

Persist the run↔file evidence relationship (`agent_run_files`), expose evidence lists + `source_type` through the existing API surfaces, and add the reserved `whatsapp` source value.

## Files to Modify/Create

- `backend/modules/payments/models.py` — new `AgentRunFileRow` → table `agent_run_files` (columns per design.md Data Structures)
- `backend/modules/payments/repository.py` — `link_source_files(bill_source_id, evidence: list[tuple[UUID, EvidenceRole]])`, `attach_run_to_evidence(bill_source_id, run_id)`, `list_evidence(run_id | bill_source_id) -> list[EvidenceFileView]`
- `backend/contracts/files.py` — `EvidenceFileView`, `EvidenceRole` literal (`archive|primary|secondary`)
- `backend/contracts/bills.py` — `BillSourceType.WHATSAPP = "whatsapp"`
- `backend/contracts/inbox.py` — `InboxEmailView.source_type`, `InboxEmailDetail.evidence`
- `backend/contracts/payments.py` — `PaymentRunStatus.evidence`, `BillDetail.evidence`
- `backend/modules/payments/service.py` — `start_run` accepts the evidence links; run status endpoints join evidence
- `backend/modules/payments/runner.py` — stamp `run_id` on the source's evidence rows at run start
- `backend/modules/inbox/{service,repository}.py` — surface `source_type` (from the linked `bill_source`) and `evidence` on list/detail
- `backend/modules/bills/…` (BillDetail assembly) — include evidence
- `backend/alembic/versions/product/` — autogenerated migration for `agent_run_files` (and module 02's `files` columns if not already migrated)
- `backend/api/routers/{payments,bills,inbox}.py` — no new routes; enrich existing responses

## Implementation Guidelines

Linking lifecycle:

1. **Intake** (inbox pipeline / `start_file_run`, module 03) → `link_source_files(bill_source_id, [(file_id, role), ...])` right after `bills.register_source` succeeds. Rows have `bill_source_id` set, `run_id` NULL.
2. **Run start** (`PaymentsService.start_run` → runner) → `attach_run_to_evidence(bill_source_id, run_id)`: `UPDATE agent_run_files SET run_id = :run_id WHERE bill_source_id = :sid AND run_id IS NULL`. Also covers re-runs (a second run gets its own rows only if new files arrived; existing rows keep the first run_id — acceptable, evidence is immutable).

`list_evidence` joins `files` for `filename/mime/size_bytes/scan_status/created_at` and orders by `role` (primary first) then `created_at`. Orientative:

```python
async def list_evidence(self, *, run_id: UUID | None = None,
                        bill_source_id: UUID | None = None) -> list[EvidenceFileView]:
    stmt = (select(FileRow, AgentRunFileRow.role)
            .join(AgentRunFileRow, AgentRunFileRow.file_id == FileRow.id)
            .where(...))
```

For the inbox list (`InboxEmailView.source_type`): the email already relates to its `bill_source` via `bill_sources.inbox_email_id`; resolve `source_type` from it, defaulting to `email` when no source row exists (pre-existing rows). Keep the list endpoint N+1-safe: one query for sources of the page's email ids.

`whatsapp` value: enum-only addition. `WHOLE_CONTENT_HASHED_SOURCES` (`modules/bills/service.py:32`) — check whether the set needs the new value; from its name it hashes whole content for non-attachment sources, so `whatsapp` (like chat/telegram) likely belongs in it. Follow how `telegram` is treated everywhere it appears and mirror that.

Self-check: after a simulated email with ZIP → `GET /inbox/emails` rows carry `source_type: "email"`; `GET /inbox/emails/{id}` returns evidence `[primary xml, secondary pdf, archive zip]` with `scan_status`; `GET /payments/runs/{id}` includes the same evidence with `run_id` stamped; `GET /bills/{bill_id}` detail includes evidence.

## Integration Notes

- `EvidenceFileView` is the single wire format consumed by module 06 (evidence list UI + badge). `scan_status: clean` drives the "Escaneado por AWS" badge; `unsupported` → "Sin escaneo"; anything else → treat as blocked (should not appear on decided bills).
- `bill_sources.file_id` remains populated (primary file) for the existing duplicate-navigation logic in `DecisionCard.tsx` — do not remove it.
- `source_type` values and their UI labels are owned by `frontend/src/lib/labels.ts` (module 06); backend never sends display labels.
